# Claude Approvals: explain a policy, look up a key

A reference file of the skill \`claude-approvals\`. Read \`SKILL.md\` first: everything there above "Workflow" binds here too. A section named in quotation marks that this file lacks stands there. \`SKILL.md\` and \`references/...\` count from the skill's folder, not from the repository.

**Contents:** Explain a key or a rule; What happens to this pull request; Why is the check red, waiting or missing; After a failed Code Review: when a resolve counts; What the files cannot tell you; Keys; Messages.

## Explain a key or a rule

Explain from the file in front of you. Read a rule out in this order:

1. **Which files:** \`paths\`, less what the \`"!"\` items leave out.
2. **Which pull requests:** its own \`if\`, or "every pull request".
3. **What it asks normally:** its own \`verdict\`, in people: "the author and one more person", not "two seats".
4. **When it asks for something else:** each override from the top, as "if ... then ...".
5. **What happens with no result:** as "How a policy decides", point 3, says, for the rule's own \`if\` and each override. Say it each time.
6. **What else matches the same files:** other rules apply too, and the strictest wins.

Fill in \`use\` and \`"@name"\` first. Fields written in place win over the \`use\` map's, and an \`override\` list written in place replaces the map's. A chosen override still replaces each field that it writes.

Answer the question in the first sentence. For a key, give what it does, its default, and a line from the user's file. If the file holds a key this skill does not describe, say you cannot explain it; do not guess from its name.

## What happens to this pull request

Walk these steps and write them down; skipping one invites wrong answers.

1. **List the changed files.** A moved file counts at its old and its new path. After a push, a rule that covered only a file that has left the pull request stops applying. A draft is not evaluated until marked ready, unless Claude's approval stands on its latest commit.
2. **For each file, find the policy file that decides.** Start in the file's directory and go up. Pass over a policy file that observes. Stop at the first file in which a rule with a \`verdict\` applies (step 3). Also stop at a policy file where the only rules with a \`verdict\` that apply are enforced \`nested: inherit\` rules from files above, if that policy file covers the changed file, protected or not: an enforced rule of its own with a \`verdict\` matches it, even one whose \`if\` is false. The unmarked rules above then do not apply.
3. **List the rules that apply:** \`paths\` match, no \`"!"\` item takes the file out, not \`mode: observe\`, own \`if\` true or absent. Add matching \`nested: inherit\` rules of enforcing files above. Then:
   - **No enforced rule with a \`verdict\` matches, up to the root:** the file is **uncovered**. Nobody is asked to review it, unless it is protected and a policy file above it, or above another changed file, enforces a rule with a \`verdict\`: then it waits for one person. Claude does not approve, and the \`pr/\` counts still take it in. If every file is uncovered and none is protected, the check mostly ends neutral (exceptions: "Did not run", below).
   - **Rules match, but each \`if\` is false, up to the root:** red, "No rule applies". A protected file waits for one person instead.
   - **A rule's own \`if\` needs a result that never came:** red, whoever approves, unless another part of the \`if\` settles it.
4. **Pick each rule's verdict.** Read its overrides from the top:
   - False: read on. True: chosen; lay its fields over the rule's verdict, and stop.
   - Its classifier is running or has not started: the rule waits. Promise no length of wait. After a Code Review that ended in an error, Claude Approvals can ask for it again by itself for about two hours: unless the check goes green first (step 7), it stays in progress meanwhile, and what the file asks on an error holds only after that. Once the check stops waiting, a run with no result mostly reads \`error\` (a run whose answer Claude Approvals dropped or put off, and a few other cases, read neither \`error\` nor \`incomplete\`: "How a policy decides", point 3).
   - \`= error\` or \`= incomplete\`, and the run ended that way: chosen.
   - Any other comparison with no result: stop. It lacks a result; it is not false. The rule's own verdict holds until a result arrives; a late fail can turn a green check red. Exception: an override on \`claude/code_review.severity\` can still be chosen where Code Review has left a thread, so one that says \`blocks\` can keep the check red. It is read only if nothing stops the reading first: an override above it that is chosen (such as one on \`= error\`) or lacks a result (such as \`= fail\` or \`= pass\`) hides it. A \`= fail\` can also lapse with no new review, so put the strict verdict on the rule, not only on \`= fail\`.

   \`AND\` is false once one side is false, and \`OR\` is true once one side is true, even if the other side has no result.

   **Example:** a rule asks \`{ claude: comments, seats: 2 }\`, with one override, \`if: "claude/code_review = pass"\`, asking \`{ claude: approves, seats: 1 }\`. dev, with write access, changes a file that no other rule matches; the review ends in an error and the check stops waiting; nobody has approved. \`= pass\` lacks a result, so the rule's own verdict holds: red, waiting for one person.
5. **Combine.** The strictest \`claude\` wins, and every set of seats must be filled. A number N means "N from \`humans\`". A protected file asks at least one person and counts no bot. Read \`approves\` as \`comments\` if the pull request changes a symlink, a submodule pointer, a \`.gitattributes\` file, or a protected file that no rule applies to.
6. **Fill the seats,** each set by itself. One person counts in every set that admits them.
   - **The author's seat:** one person fills a seat in each set that admits them, without approving. While the latest commit is the one the pull request was opened with, the opener holds it (where somebody else wrote or pushed that commit, only until the base branch is changed, and only where the evaluation could read GitHub's list of base changes); once a later commit exists, whoever both wrote and pushed the latest commit; mostly nobody if somebody else committed, pushed or rebased it, or if that commit reached the pull request more than 14 days ago. On github.com the opener also holds it where their own account alone pushed the latest commit and that is a verified commit in the name of the account that Claude's hosted sessions commit as, unless the pull request changes a protected file. An author whose latest review since their push requests changes holds none. A bot holds it only in a set that admits it (\`bots\`, \`everyone\`, its \`bot:\` name, \`pr/opened_by\`, \`pr/authors\`), on a pull request that it opened, and only as long as it pushed the latest commit; Claude's Apps never. Where \`reuse\` keeps \`seats\`, people who held it earlier can go on counting; a change of base or a rewrite mostly ends that.
   - **An approval counts** if given on the latest commit by an account with write access (but not where the check reads "Branch out of date; update it"). A change or force-push of the base branch, or a reopening, can end it. After a push it counts only if the diff stayed identical or \`reuse\` keeps it, so mostly not where no policy file above the change writes \`reuse\` at all; a review that GitHub dismissed at the push counts only on a changed diff whose \`claude/diff\` rating meets a \`seats\` condition, with no other classifier read to keep it. An approval is kept or dropped whole: one rule that applies to a file changed since, could count that person and does not keep it by its own \`reuse\` drops it for all rules. While a rule on any file of the pull request reaches an override that it cannot judge, because its classifier ended with no result, and says \`blocks\` there or below, mostly no approval from before the push counts, unless that override or one above it catches \`= error\` or \`= incomplete\`.
   - **\`@claude approve\`:** a new comment by a person with write access holding nothing but \`@claude approve\` and the latest commit's full SHA (not edited, hidden or sent by e-mail) counts as their approval (not toward GitHub's own required approvals). Without the SHA, as Claude's comment may offer it, it goes to whichever commit was the latest when it was posted, and does not always count; on a pull request from a fork it never counts, and can cancel the same person's earlier one. Tell the user that it exists; never post it yourself, even when asked.
   - \`"!pr/authors"\` leaves out everyone who wrote or pushed a commit, and the opener, by the accounts that GitHub names: not a person whose agent did all that under another account, nor one named only in a \`Co-authored-by\` line. Either's approval counts in such a set: say so. Where a commit names no account, whoever pushed it stands in for its author (the exception, on a pull request that a bot or Claude's App opened: "Cannot tell who wrote this change", below).
7. **Read off the check.** Green: nothing blocks, every set is full and no \`max_age\` has run out. In progress: not green, and a rule waits for a run (a classifier only under \`advisory\` is not waited for), or Claude Approvals itself is not done, mostly waiting on GitHub. Red: everything else, including waiting only for people. While runs go, the check is green if the approvals in hand meet every verdict the rule could still pick. It is red already where a rule that applies blocks however they end. Such a green can come with no Code Review asked for (\`references/tune.md\`, "What runs when"). A request for changes by a person with write access mostly turns a green red, so beside such a request that still stands, say that the green may be out of date. On some pull requests (from a fork, or opened by a person without write access) a green also waits for a person with write access to approve: never promise that wait, or count on it to ask nobody. It takes somebody other than the opener, on the latest commit or an earlier one since the diff last changed: an approval that only \`reuse\` keeps, a rerun, or the holder of the author's seat does not end it. A merge queue's own commit mostly gets a passing check at once, with nothing judged: once a pull request is queued, its own check, red or unfinished, no longer stops its merge.
8. **Does Claude approve?** Only if the check is green and the combined \`claude\` is \`approves\` for every result a running run could give. Where every rule that applies says \`approves\`, a seat that Claude's approval may fill already counts as filled while the check is judged, even where an uncovered file means that Claude never approves, so the check can turn green with fewer people than that set names. Where any rule that applies says \`comments\`, Claude's approval fills no seat. GitHub can count Claude's approval as a required approval, so where GitHub asks for one approval and the verdict says \`approves\`, a pull request can merge with nobody but its author looking wherever the author's seat and Claude's approval fill every set (\`seats: 0\` or \`1\`), and with no person approving where past holders of that seat fill the rest (\`2\` or more where \`reuse\` keeps \`seats\`).

   **Stale approvals.** Where GitHub requires approvals and neither "Dismiss stale pull request approvals when new commits are pushed" nor "Require approval of the most recent reviewable push" is on, GitHub keeps counting Claude's approval after a push until Claude Approvals withdraws it, which can come late or never, and GitHub can refuse the withdrawal: unreviewed code can merge meanwhile. Where the warning "This branch seems to keep stale approvals" shows, or you learn both are off, tell the user once and recommend one of the two settings and the required check, with the price: "Dismiss stale..." dismisses everyone's approvals at a push that changes the diff; the other can be met by Claude's approval, but where Claude gives none (say, a rule says \`comments\`) GitHub can want someone other than the author or the last pusher to approve the newest push, even where the check is green on an earlier approval; that setting also leaves the old approval up, so a refused withdrawal can still stop the check. A missing warning does not show that a setting is on. The choice is theirs.

## Why is the check red, waiting or missing

Read the title and summary: \`gh pr checks <number>\`, and \`gh pr view <number> --json files,author,reviews,commits,baseRefName\`. Match on the fixed words. Under a file that observes, the check ends neutral, its title opens "(observe mode)", and the rest mostly begins with "Would"; one that says "Withheld" is not neutral: it asks for action, and the summary says what clears it. (A pull request that changes a policy or classifier file gets a real check instead; most other pull requests into a branch other than the default get none.) For a title not listed below, the summary gives the cause and what to do. Offer each fix below; make it only as "Start here", point 2, says. If a fix could make merging easier, ask the user. Never edit a policy file only to make a title go away.

- **"Waiting on human review" ...:** people are missing; nothing in the code needs fixing. The summary says who; the title's count can leave some out. Look for an approval from before the last push, an approver without write access, a set that names a team or leaves authors out, a second rule that asks more, a protected file, a bot as author or opener, a later commit somebody else pushed or rebased, a green that waits for a person with write access ("What happens to this pull request", step 7).
- **"Changes requested":** that person's approval of the latest commit, their own comment that the summary offers instead of an approval (a later push can bring the request back), or a dismissal of their review clears it. A person's dismissal counts, but not a bot's, Claude's, or one where GitHub does not say who made it. A review can be dismissed only once: after a dismissal that does not count, only that person can end the request. Never dismiss a review unasked; asked in a Claude session, have the person dismiss it.
- **"Nobody on a rule's list can approve here", "Too few on a rule's list can approve here":** the list holds only bots, and a protected file changed; or it holds only logins, and too few of them have write access. A wider list lets new people approve: propose it, make it only on the person's word.
- **"Cannot tell who wrote this change", "Could not read who wrote this change", "Too many commits to tell who wrote it":** a set that is still short leaves authors out (\`"!pr/authors"\`), and until Claude Approvals can name every author, no approval counts toward that set, whoever gives it: more approvals do not help. Under "Cannot tell", one cause: on a pull request that a bot or Claude's App opened, a commit whose author or committer GitHub ties to no account; a rebase keeps its author, so may not help. Offer the summary's steps in order; two ask for less, so take them only on the person's word: \`"!pr/opened_by"\` in place of \`"!pr/authors"\`, and a merge past the check. Taking \`"!pr/authors"\` out would let approvals count, but would let authors fill that seat on every pull request under that rule: do not offer it as the fix.
- **"Results are older than the policy allows":** a rule's \`max_age\` has run out ("Keys"). Nothing in the code needs fixing and no person's approval has expired: offer a rerun, or a push that changes the diff.
- **"Waiting for" a classifier, "Waiting for classifiers":** wait.
- **"Code Review timed out", "Required signal unavailable":** a later title may follow; go by that. A rerun, or \`@claude review\` from a person with write access where Code Review is on for the repository, can help.
- **"Held by" ...:** a verdict says \`blocks\`. Find the override that would open it. No approval helps, unless that override reads \`pr/approved_by\`.
- **"had no result":** mostly a rule's own \`if\` needs a result that never came. Or a \`repo/\` classifier had no result while Code Review, read below it, was held back and no review came (\`references/tune.md\`, "What runs when"). Or the rule's own verdict blocks: a rerun may help; no approval helps, unless an override above that one reads \`pr/approved_by\`. A push that changes the diff, or a rerun, starts a new run. To fix it for good, where the classifier stands in the rule's own \`if\`: move it into an override, keep the rule's own verdict strict, and say who must approve before and after.
- **"has not run", "have not started", "reached its run limit", "reached the run limit":** no result counts and mostly no run starts by itself. The limit is 10 repeat runs on one diff, then one more for each rerun. The push's own run and some others do not count. Nothing runs on a push from an account without write access, until a person with write access comments \`@claude approvals rerun\`: a check that needs a run to pass is red meanwhile. Exception: where Code Review skipped a commit that brought no change of its own, Claude Approvals may ask for the review itself (billed), so wait a few minutes, and rerun only if no review has started; where the summary says that Claude Approvals did not request a review itself, follow its step instead. A rerun may help once (billed), or set Code Review, in its own settings, to review every push (a review at each push; no help at a run limit). Where the summary says that Code Review refused the request, neither is likely to help. A run limit resets at a push that changes the diff. Where the summary says "This check can still pass on people's approvals" and gives a number, that many more approvals turn it green. Otherwise do not promise that an approval turns it green.
- **"Code Review did not run for a billing reason":** no edit mends it, and a review that is asked for may be refused again until the cause is fixed. Code Review's own check, "Claude Code Review", says what to do; an Owner of the Claude organization sees and changes the spending limit at claude.ai/admin-settings/usage. As under "has not run", promise a green on approvals only where the summary gives a number.
- **"Change too large to evaluate":** GitHub shows 2,000 changed files or more, or the files lie in too many folders. No approval helps. Follow the summary: if far fewer files really changed, the count is stale, the base branch wrong or the branch behind it, so correct that, then push or rerun; else split the pull request.
- **"No rule applies to" a file:** offer a rule with no \`if\` for it.
- **"Nothing ran, not blocking: no file is covered", "Seat filled, not blocking: no file is covered":** no enforced rule with a \`verdict\` matches; the neutral result passes even a required check, so the pull request can merge with nobody else asked. Say so, and offer a rule whose \`paths\` match.
- **"Passed; no approval from Claude":** the check passed, and Claude posted no approval. A seat that Claude's approval may fill can count as filled, so fewer people may have approved than the rules ask. Read the summary for the cause ("Green, but Claude did not approve", below).
- **"Did not run: ...", or no check:**
  - A name that cannot be parsed: rename it.
  - A file renamed between a covered and an uncovered path, or copied from an uncovered to a covered one: two pull requests, one adding the file under its new name, one removing the old; say nobody reviews it under an uncovered name.
  - A branch other than the default, a fork, an opener without write access: a matching rule, merged first.
  - A commit shared with another open pull request or a fresh policy change: a push or rerun.
  - A failed read of GitHub, which the check may not name: wait some minutes, since Claude Approvals mostly tries again, then offer a rerun, or as a last step a push, which can cost approvals.
  - Changes requested: the reviewer approves in a review.
  - "the policy file only observes": a neutral result mostly follows by itself (else a push or a rerun brings it), and then gates nothing.
  - "no policy file found": the default branch has no policy file at the root or in a directory above the changed files, most often because every policy file was removed to turn Claude Approvals off; other directories may still hold some. Where the check is required, it holds the merge, and new commits get no check. To stop using Claude Approvals in the whole repository, somebody who can edit the branch rules stops requiring the check. To keep it, a policy file on the default branch with a rule whose \`paths\` match these files brings a result at the next commit: write it only on the person's word, from one of the starters in \`SKILL.md\`.
- **"This change breaks a policy file":** fix it in this pull request ("Messages").
- **"policy file cannot be used", "policy files cannot be used", "policy file must be version 1", "policy file is too large", "did not parse":** the default branch's copy blocks every pull request under its directory, the fix too. Read the summary for the cause, and do what it says, but if that could make merging easier, ask the user. A broken or refused file: repair it to what it last asked. Too large: shrink it by the safe rewrites of \`references/tune.md\` (comments, locals); past that, deleting what matches no file today or widening a pattern changes what it asks: propose it, and say what it newly matches. Either way, somebody who can bypass the branch rules must merge the fix. If the fault is Claude Approvals' own, change nothing and report it to Anthropic.
- **"Custom classifiers are not enabled here":** a policy file names a \`repo/\` classifier where none may run, so the whole file is refused: see the end of "Messages".
- **"Cannot evaluate: classifier outside advisory":** the pull request changes a file under a directory that has its own policy file, and that file or one above it names, outside an enforced rule's \`advisory\` and the keys of \`findings\`, a \`repo/\` classifier that has an input under \`unset\` (no \`merge\`, or \`merge: unset\`), or \`labels\` or \`reviewers\` among its \`tools\` (\`references/classifiers.md\`, "Monorepos, names and versions"). No approval helps. Offer the summary's ways out, and say what each changes.
- **Classifier titles:** "definition cannot be used": a pull request from a branch of this repository that changes the definition shows why. Repair it if it is at fault (\`references/classifiers.md\`). Where the summary says that Anthropic hosts the classifier, nobody in the repository can repair it: wait for Anthropic's fix, after which a push, approval or rerun updates the check, and loosen nothing meanwhile. "result is out of date": a rerun. "result no longer counts": wait, unless the summary says the classifier reached its limit (then a push that changes the diff, or a billed rerun). "No classifier result counts on this commit": where the summary says Claude Approvals may ask the code host again by itself, wait first, since a push can cost approvals; results can count once somebody with write access pushes a file-changing commit to a branch in this repository, or runs the summary's rerun.

**A rerun:** a person with write access comments \`@claude approvals rerun\` or clicks Re-run. It can drop results and bill runs again. On a fork only the typed command works, and only once the check has reported on the fork's latest commit. Never promise that it turns a check green.

**Turning Claude Approvals off** for the repository, in the admin settings, ends every rule there: a check that the branch requires then cannot pass, and elsewhere none of its rules holds a merge back.

**Which checks to require.** Once "Claude Approvals" has reported, require it from the App that reported it, not "any source". Never require "Claude Approvals Config", which most pull requests never get, or "Claude Approvals (observe)", which nothing posts any more. While the file observes, the check ends neutral and gates nothing but a few pull requests (\`SKILL.md\`), and most pull requests into a branch other than the default get no check: say so to a user who requires it early, and do not require it on such a branch yet.

A policy file that does not say \`version: 1\` is not described by this skill: say so, and change nothing in it unasked.

**No check, and a comment that Claude Approvals "can't start in this repository yet":** the repository's Claude organization "has no usage credits available to pay for it". No file is at fault: edit nothing. An owner of that organization "can add usage credits or raise its monthly spend limit at" claude.ai/admin-settings/usage. Pass on whatever else the comment offers, and its steps for afterwards: wait "at least ten minutes", merge the pull request that adds the root policy file if the default branch has none, then open or push to a pull request that isn't a draft.

**No check at all,** in order: usage credits that cannot pay (the comment above); no policy file on the default branch yet; a draft; a "Did not run" cause; no root policy file and every changed file outside the directories that have one; the file observes, the pull request changes no policy or classifier file and adds no path that could keep one from being read, and goes into a branch other than the default; no push or approval since the policy file was merged; no repository of the Claude organization has had a root policy file on its default branch, so a directory's file alone might not start Claude Approvals (a root file there, even one that only observes, mostly does). Otherwise the cause lies outside the files: for one, nothing is posted for a Claude organization that is not on a Team or Enterprise plan, or that has Zero Data Retention enabled or the HIPAA configuration applied, or that some other compliance settings keep out. With no policy file yet, offer a starter (\`SKILL.md\`).

**One of Code Review's threads is resolved, and the check stays red or the thread is open again:** see whether a \`findings\` list lets that person or bot resolve; with no list at all a resolve mostly does not count (\`findings\`, below). If a list names them, see "After a failed Code Review: when a resolve counts". If none does, Claude Approvals can re-open the thread and say why in a reply; it does not re-open every one, so silence proves nothing. Two cases are silent by design, the thread staying resolved and the finding still counting: the thread's first comment was edited or deleted, or its severity cannot be told and the lists for \`high\` and \`minimal\` differ. With no edit: un-resolve the thread if it still looks resolved, then fix the finding and push, or, if it is wrong, say why in a reply. No reply brings a review: a push or a person's \`@claude review\` does. A review looks again at the threads that are open when it starts, and can then close this one. It mostly looks too at those whose resolve the policy file refuses, and can pass on a fixed one, though the thread stays as it is and Claude Approvals may still re-open it. With an edit, on the person's word: a list that takes them in, their login or most plainly \`findings: { resolution: { claude/code_review: humans } }\`, which lets every person with write access resolve, the author too, with nothing fixed (\`[humans, "!pr/authors"]\` leaves authors out). Follow \`SKILL.md\` to write it ("Who may dismiss a finding": where it goes, and the guard that it needs). Once it is merged, a listed person's resolve counts, an earlier one too while the thread still stands resolved ("What no resolve clears" aside).

**Green, but Claude did not approve:** among the causes, a rule says \`comments\`; a symlink, submodule, \`.gitattributes\` file or a protected file that no rule applies to changed; a file is uncovered; a classifier still runs; Claude's own App wrote the change.

**Green, and GitHub still blocks the merge:** GitHub's own branch rules can want a review that the policy does not: a code owner's, one more, or a newer one. Claude's comment may then say "GitHub's branch rules still need"; the merge box names the rule. After a push, "Dismiss stale..." and "Require approval of the most recent reviewable push" can want a newer approval even where the check counts the earlier one: have someone other than the author or the last pusher approve on GitHub (\`@claude approve\` does not count there). This wait is no reason to loosen the policy or to switch either setting off.

## After a failed Code Review: when a resolve counts

- **Who.** For \`.severity\`, the lists of the rules on the thread's own file decide, not those on the pull request's other files, unless no enforced rule covers that file (and, if it is protected, no policy file at or above it enforces a rule with a \`verdict\`), or the pull request no longer changes it: then the rules of every covered file are asked (\`findings\`, below). The answer (\`= pass\`, \`= fail\`, \`!=\`) is one for the whole pull request, so it asks more: the account must also be on the lists of every changed file under a rule that compares the answer, in a \`reuse\` condition too (not a rule whose \`if\` is false, nor one that a directory's own policy file overrides there). While nobody may resolve on one such file (\`nobody\`, or no list reaches it), or an account whose resolve closed one of the failed review's findings is not allowed there, the review goes on reading \`= fail\`, though \`.severity\` falls thread by thread. So \`nobody\` on a sensitive path keeps a block on \`= fail\` on every pull request that touches that path, wherever the findings sit, for as long as the failed review stands ("What no resolve clears"). Where the lists only differ, the check can still offer the resolve, and says "the failed review still stands" once somebody who is not allowed there has resolved. (\`@claude approvals resolve\` is judged by the lists on the finding's own file or, for a finding on a file that the pull request does not change, on every changed file. Later evaluations no longer know who typed it. So the close turns the answer only where the files under a rule that compares the answer bring no list beyond those that the command was judged by: any other list keeps the review a fail, even one that names the same person. So do lists that are not certain, there or on the finding's own file: a rule with a list of its own whose \`if\` depends on a classifier, an override whose list differs from its rule's, or lists that differ by severity. Where the finding has a thread, a click on Resolve by a person on all those lists turns the answer.) Whether the finding is fixed decides nothing. Under \`everyone\` or \`bots\` a bot needs write access, as a person does (one that a list names, \`bot:name\`, counts by that name). Under either of Claude's Apps, a resolve of a thread of Code Review's own counts where those lists take Claude's App in (\`bots\`, \`everyone\` or \`bot:claude\`, with no \`"!bot:claude"\`, and no \`"!pr/authors"\` where Claude's App wrote commits of the pull request). On a pull request that one of Claude's Apps opened it may count or not, so promise neither: \`"!pr/authors"\` or \`"!bot:claude"\` on those lists keeps it out for certain. On GitHub nothing tells Claude's sessions apart, so such a list lets in every Claude session that resolves under Claude's Apps. Under any other list, or none, a resolve under Claude's own accounts closes nothing in an evaluation (under the user account of Claude's sessions, whatever the lists say). Code Review's own judgement is the exception: a thread whose closing one of its reviews recorded, as where a push fixed the finding, counts as closed under every list, \`nobody\` and none too, once the review of the newest commit (or the one that a \`reuse\` line keeps for it) has passed or failed, no earlier than that closing. Until then, and where that review ends in an error or is skipped, it counts by the lists, as any other resolve under Claude's Apps. Of a later review promise nothing. Where an enforced rule reads \`claude/code_review\`'s answer or its \`.severity\`, a person on the lists can also close a finding with \`@claude approvals resolve\`; if the reply says that it could not, they follow the reply.
- **The bot that opened the pull request** (not one of Claude's Apps: "Who", above) counts only while Claude Approvals can confirm that it pushed the latest commit itself: after somebody else's push (such as another account merging the base branch in, or "Update branch") or a change of base its resolves stop counting, and after a failed read of GitHub they can count in one evaluation and not in the next. Where a thread that it resolved reads "looks resolved, but Claude Approvals does not count that", though it pushed the latest commit itself and nothing has moved since, a read may have failed: wait twenty minutes and read the check again (a failed read is mostly retried); do not push, and do not un-resolve. Where the row says instead that the bot that opened the pull request resolved the thread, read the summary's note above the threads. Where it says to wait, wait as long as it says, then read it again: meanwhile no push, no new resolve, no request for a review. Where it gives no step, follow the "To resolve:" line, but ask the user before posting \`@claude review\`. Where the note says to have the bot push one new commit, ask the user first; they may prefer a fix. Only the bot's own push gets its resolves rechecked; the finding can then close unfixed, Code Review may run again and people may have to approve again. If the bot's row still stands once the check finishes on its new commit, or a thread still reads "looks resolved" after twenty minutes, tell a person, who can fix the finding or, if the lists let them, un-resolve the thread and resolve it themselves ("What no resolve clears" aside).
- **What it changes.** A resolve that counts does so at once, at the evaluation that it starts, and no review follows. It lowers \`.severity\`, and it can turn the answer: a failed review reads \`= pass\`, and \`= fail\` is false, once accounts allowed across the pull request ("Who") have closed every finding that it counted, or only nits are left open (Code Review itself passes beside open nits). The pull request then gets whatever the file gives \`= pass\`, fewer people and Claude's approval too, with nothing fixed and no second review; the check marks that pass "failed review, blocking findings resolved per policy", and Code Review's own summary may still list them until its next review. After a fail, \`.severity\` reads \`none\` only once none of Code Review's threads counts as open, nits too; after a pass, \`= pass\` holds whatever is open, and an open nit reads \`minimal\`. The check waits only where a review of the pull request is already running, or Claude Approvals could not read whether one is: it shows In Progress for that review, for the organization's wait or 30 minutes, whichever is longer, and then decides on the resolves. Where the failed review is of another commit with the same diff, it waits for the organization's wait alone, or not at all where no review of the latest commit is to come. If that review has still not reported when the wait ends, the check treats the commit as not reviewed by Code Review.
- **What no resolve clears.** The review stays a fail where those who resolved are not allowed across the pull request ("Who"); where one of its findings has no review thread (nits that stand only in the review's text aside), unless a person closes it with \`@claude approvals resolve\`; where the review did not record which findings it counted, as one that was cut short may not; where a thread's first comment was edited or deleted; where no evaluation saw a thread open after the review failed (un-resolving it and resolving it again mostly does not help: a new review can, by passing, or, if the thread is un-resolved before that review ends, by failing, after which a resolve counts); and where Code Review carried the fail over to a push with the same diff. A fail that a \`reuse\` line kept may stay a fail whatever is resolved. What the file asks on \`= fail\` then goes on applying. Where the summary says that resolving "does not unblock this check", or that "the failed review still stands", do not count on a further resolve to turn it green. The fail then mostly stays until a new result replaces it (a new review can pass once its blocking threads are closed, by a fix where nobody may resolve them), a person's rerun drops it, or a push that changes the diff or another change to the pull request drops it (some leave it standing, so don't promise it).
- **What brings a new review of the same commit.** Never a resolve: not a click on Resolve, not \`@claude approvals resolve\`, not a reply in a thread. A person with write access posts a new comment with \`@claude review\` alone on its first line (billed; on a draft only where Code Review itself hears it; never post it unasked), clicks Re-run on Code Review's own check (not on a fork, nor on a commit that two open pull requests share) or, unless Code Review runs only on request, marks a draft ready. A bot's comment or Re-run starts none, nor its "ready" at a commit that already has a review. Where Code Review is switched off for the organization, \`@claude review\` and Re-run on its check can be refused; \`@claude approvals rerun\` asks for one, but not in some organizations that never set Code Review up, where the check may still say that Code Review is off for the organization. Nor does that rerun ask for one in an organization whose compliance settings keep Claude Approvals from starting Code Review. A rerun of Claude Approvals (above) is no plain re-read.
- **What that review does.** It fails only while a blocking thread of its own stands open at its end, and a resolve that Claude Approvals can tell is not allowed reads as open there, unless that review judged the finding fixed. So a resolve accepts the finding and fixes nothing: it is the person's call, so never resolve unasked. A bare "accepted" in a thread left open closes nothing. That review looks at the pull request, not only at that finding, so it can find something else.
- **So a person who accepts a finding,** if the lists let them, resolves every blocking thread themselves, and waits for no review: the check is evaluated again by itself. If the review still reads as failed then, "What no resolve clears" says why and what ends it. Nits can stay open unless a rule needs \`.severity\` at \`none\`. A resolve made in draft counts once the pull request is ready.

## What the files cannot tell you

Who has write access or is in a team, whether and when Code Review runs, how branch rules are set, what Anthropic set up for the organization. Ask or look it up (\`gh api\`), and say what you assumed. If a correct file gets no check and no error, say "contact Anthropic support", and stop editing.

## Keys

An unknown key, or a key written twice, refuses the whole file. All keys and the words they take are lower case. A policy file is \`approvals.yml\` (or \`approvals.yaml\`, never both) in a folder named \`.claude\`. That folder cannot lie inside another \`.claude\` folder: such a file is refused.

| Where | Key | Takes |
|---|---|---|
| file | \`version\` (required) | the bare number \`1\`; \`"1"\` is refused |
| file | \`rules\` (required) | one flat list of rules; their order never matters |
| file, rule | \`mode\` | \`enforce\` (default), \`observe\` |
| file, rule | \`nested\` | \`overwrite\` (default), \`inherit\` |
| file, rule | \`run\` | \`sequential\` (default), \`parallel\` |
| file | \`locals\` | a map of names to values |
| rule | \`purpose\` (required) | one line of text; \`@name\` is not filled in |
| rule | \`paths\` (required) | a list of patterns, even for one |
| rule | \`verdict\` | \`claude\` and \`seats\`; \`max_age\` if wanted |
| rule | \`if\` | a condition (default \`true\`); \`false\` switches the rule off |
| rule | \`override\` | a list; the first true one is chosen |
| rule | \`advisory\` | classifier names or calls, with no output, a call in quotes (unquoted, a comma inside \`[ ]\` or \`{ }\` splits it); they run, are not waited for and decide nothing, unless a matching rule also reads them |
| rule, override | \`reuse\` | a condition, or a map of conditions |
| rule, override | \`findings\` | \`{ resolution: ... }\`; \`resolution\` is required |
| rule, override | \`use\` | a list of \`"@name"\`, each a local holding a map |
| override | \`if\` (required) | a condition; \`false\` switches the override off |
| override | \`verdict\`, \`reuse\`, \`findings\` | \`verdict\`: each field written replaces the rule's; \`reuse\`, \`findings\`: replace the rule's whole value, \`findings\` even where none of its sets is true |
| verdict | \`claude\` | \`approves\`, \`comments\`, \`blocks\` |
| verdict | \`seats\` | 0 to 16 unquoted, or a list of sets; refused beside \`blocks\` |
| verdict | \`max_age\` | a whole number and one unit (\`s\`, \`m\`, \`h\`, \`d\`), from \`1m\` to \`83d\`: \`24h\`, \`7d\`; \`unset\` takes it out; default: no limit |
| set in \`seats\` | \`count\`, \`from\` (both required) | 1 to 16; people, but not \`nobody\` |

- On a rule, \`mode\`, \`nested\` and \`run\` default to the file's. \`mode: observe\` at the top holds for every rule, whatever a rule writes; on a rule, the rule neither applies nor covers. A file whose rules with a \`verdict\` all say \`observe\` observes, whatever its top line says. \`nested: inherit\` keeps a rule applying under every policy file below, which cannot lower it.
- \`run: sequential\`: the rule's \`repo/\` classifiers start in turn: those of its own \`if\` first, then, if that is true, by override, those of the next override only once every override above is false (several in one condition start together); Code Review mostly starts at the push anyway, and no fact holds it back; \`parallel\`: all at once. It never changes which override is chosen for the same results; where a classifier can add reviewers, or an override writes a shorter \`max_age\`, it can change how the check ends (\`references/tune.md\`).
- A rule without \`verdict\` covers no file and asks nobody. It may leave \`verdict\` out if it holds \`findings\`, \`advisory\` or a classifier's line under \`reuse\`, and no \`override\` and no \`seats\` line under \`reuse\`. An empty \`advisory: []\` or \`reuse: {}\` alone is refused. What it holds mostly counts only on a changed file that a rule with a \`verdict\` also matches: a file that it alone matches brings no run, though Code Review can still start by its own setting where such a rule names it.
- An override takes no \`paths\`, \`run\`, \`mode\`, \`nested\` or \`advisory\`; \`purpose\` is optional. It needs \`if\` and one of \`verdict\`, \`reuse\`, \`findings\` (a \`verdict\` that \`use\` brings counts). One that writes \`findings\` alone is still an override: where it is the first true one, those below are not read.
- \`seats: 2\` is short for \`[{ count: 2, from: humans }]\`; \`0\` asks nobody. So does \`[]\`. \`from: [a, b]\` takes someone from either: for one from each, write a set for each. Under a rule that blocks, an override that writes \`approves\` or \`comments\` must write \`seats\` too. A \`count\` above the number of logins is refused where \`from\` holds only logins.
- \`max_age\` limits how long the check's result stands. No person's approval expires by age. The time runs from the pull request's first evaluation, or from an older result that it counts. Soon after it ends, with no push, the check turns red ("Results are older than the policy allows") and Claude's own approval is withdrawn. A rerun by a person with write access, or a push that changes the diff, starts it anew and can run the classifiers again, billed. An approval, an identical push, a new base branch or a reopening does not, and a result that \`reuse\` keeps over a push goes on ageing from its own run. Of the verdicts chosen, or that a waiting override could still choose, the shortest age holds. A longer age, or \`unset\`, asks for less. Taking the key out of the file does not clear a check that has already turned red by age.
- \`unset\` takes a key out, as if it had never been written. It stands for \`max_age\`, for \`resolution\` whole, and for \`reuse\` whole or one name under it. In an override it takes away what the rule holds (for \`resolution\`, not where the override only narrows: \`findings\`, below); on a rule, what a map brought by \`use\` holds. It reaches no other rule. Where it has nothing to take out, a note says so.

**\`findings\`** says who may close a classifier's finding by resolving its thread, so that \`.severity\` stops counting it and Code Review's failed review, with its blocking findings closed, reads \`= pass\`. **With no list, no person's resolve counts** toward either. The list is for people and bots who close a finding against the classifier's judgement: a finding that a later run of the classifier itself closes stops counting whatever the list says (for Code Review, on the conditions in "Who", above). For Code Review, count on having no list only where an enforced rule with a \`verdict\` and no \`if\` on the finding's file, in the policy file that would decide there if every rule's \`if\` held, itself reads Code Review. There a review treats a blocking thread that a person or another bot resolved before it started as open: it mostly checks the finding again, so a fixed one can pass and an unfixed one fails it (what helps: see "Why is the check red, waiting or missing"). Elsewhere, to shut people out write \`nobody\`, on a rule with no \`if\` of its own that covers the finding's file.
- **Every list but \`nobody\` makes merging easier where a condition reads \`.severity\` or compares Code Review's answer:** resolved threads can make \`.severity\` \`none\`, and a failed review \`= pass\`, with nothing fixed and no new review. Say so, and write a list only on the person's word, beside \`verdict\` on an enforced rule with no \`if\` that already covers those files (none: change nothing, and ask). Never on a new rule or one changed to fit, except the copy and guard of "The review rules themselves", and \`SKILL.md\`'s rule with the neutral verdict.
- \`resolution\` takes people, a list of sets, or a map of classifiers' bare names to either: \`{ claude/code_review: [acme/leads, "!pr/authors"] }\`. A classifier left out gets no list. No word stands for all the others, and a list under a name does not reach that classifier's other versions (\`repo/x@2\` takes a key of its own; a map that names one version and leaves out another that its file uses draws a warning). One list for all only where the person means every classifier (where a \`repo/\` classifier reports findings, read \`references/classifiers.md\` first). Each person needs write access.
- A list that takes in an author (\`humans\`, \`everyone\`, \`pr/authors\`, their team) lets them close findings on their own change. On the threads of \`repo/\` classifiers Claude's own accounts are the exception; on Code Review's, on a pull request that one of Claude's Apps opened, they may be, so promise neither ("People", below). Asked for "anyone", write \`[humans, "!pr/authors"]\` and say how to let authors in. A list the person gives as YAML goes in unchanged; say whether it takes in the author.
- Only the rules that apply to the finding's own file are asked (to turn Code Review's answer, also those of every changed file under a rule that compares it, which is what makes \`nobody\` on a sensitive path hold on a pull request that also changes other files: "After a failed Code Review: when a resolve counts"): an account must be on every list that they give, and a rule with none has no say. For a finding in a file that no enforced rule covers (a protected one only where no policy file at or above it enforces a rule with a \`verdict\`), or, by the typed command or for a thread of Code Review's that its failed review still counts, in one that the pull request no longer changes (no other thread's resolve counts once its file has left), the rules of every covered file in the pull request are asked, and a covered file whose rules give the finding no list admits nobody. **Deleting a narrow list beside a wide one lets more in.** A list on \`"**"\` reaches \`.claude/\` and the protected files: add the guard that "The review rules themselves" asks for, and lead your reply with the reach (\`.github/\`, \`CODEOWNERS\`) and that \`.severity\` is one value for the whole pull request. Add the guard beside the copy too, even where the old rule had a list: the copy has no say on a classifier that it gives no list. Ask before adding any other list to the guard, or to a rule whose \`paths\` name \`.claude/\`. Where a condition compares Code Review's answer (\`= pass\`, \`= fail\`, \`!=\`) and none reads its \`.severity\`, a new list of Code Review's, or one whose \`paths\` change, other than \`nobody\`, needs the guard and no copy if its \`paths\` can reach a file on the guard's four paths that no list of its on an enforced rule in that policy file reaches yet (\`"**"\` above all; \`src/**\` can reach \`src/REVIEW.md\`), and so does an edit that lets anybody new resolve on such a file that a list of Code Review's reached before the edit. Where no condition reads either, a list written under Code Review's name needs no guard, until an edit adds the first condition on its answer. Follow "Who may dismiss a finding" in \`SKILL.md\` for what to write and what to tell the person, in place of the lead above.
- Under an \`if\` that reads a classifier, a list only narrows, unless facts alone settle that \`if\`. The account must then also be on another rule's list for that file, or nobody may resolve. A list in an override below one whose \`if\` reads a classifier only narrows too, though facts settle its own \`if\` (unless they settle the one above as well), and nothing warns of that. Count on neither a list that only an override writes nor one on a rule with an \`if\` of its own other than \`true\`. Under an \`if\` on a fact, whoever can change the fact can switch the list (not for a \`repo/\` classifier with findings that the rule reads with the fact at or above the last override that reads it, where the fact never chooses who may resolve: see "A fact beside a classifier's findings", below). \`unset\` in an override drops the rule's list. It takes nothing away where that override only narrows.
- Sets under \`resolution\` take \`if\` and \`from\` (which may be \`nobody\`), no \`count\`. They make the list differ by severity: \`findings: { resolution: { claude/code_review: [{ if: "finding/severity >= high", from: [acme/leads, "!pr/authors"] }, { from: [humans, "!pr/authors"] }] } }\`. The first true set decides; where none is true this rule gives the finding no list and has no say: another rule's list decides alone, or nobody may resolve; nothing warns. So end with a set with no \`if\` (\`{ from: nobody }\` shuts the rest). A set's \`if\` may read facts too; one that needs a classifier's result gives no list and only narrows, and reading goes on to the next set: \`[{ if: "repo/risk.tier = high", from: acme/security }, { from: everyone }]\` admits only \`acme/security\`. Where an enforced rule on a changed file gives a classifier a set with an \`if\`, a closed finding that a later run reports as more severe stays closed only if whoever closed it may resolve at that severity; else it counts again, and nobody is told. \`finding/severity\` (\`minimal\` to \`critical\`) only in a set's \`if\`. It takes all six operators, and is the severity of the finding being resolved, not \`.severity\`, a run's worst; one that is lost reads \`critical\`. Refused: a set that fits every finding anywhere but last, or two such sets; any other set no finding can reach (a last set with no \`if\` that no finding can reach loads, with a "never used" warning); more than 16 sets. Refused too: \`finding/severity < minimal\` or \`> critical\`; a set outside a list; a list that mixes sets with accounts; \`[]\`, or an empty map; \`unset\` under a name or in \`from\`; a key that is a call, names no classifier, or names one that reports no findings (\`claude/diff\`); more than 10 teams under one key. Warned of: \`bots\` in a list that leaves out some people with write access; \`pr/authors\`; \`<= critical\` or \`>= minimal\`; a set, or an override with \`findings\`, whose \`if\` reads a classifier (it only narrows); for a \`repo/\` classifier, a set whose \`if\` reads a fact other than \`pr/opened_by\`, since whoever can change that fact can switch who may resolve.
- **\`@claude approvals resolve\`** on a new comment's first line, followed only by one to eight finding IDs (like \`f-1a2b3c4d\`, shown at the foot of the finding's thread or in Claude Approvals' comment), closes those findings: a \`repo/\` classifier's, and some of Code Review's. Only a person can type it, and the same lists decide, though the command can be refused where a click counts. It is the only way a person closes a finding that has no thread: one tied to no file, one that a failed Code Review lists only in its review's text (within limits), one past its classifier's 16 open threads, one on a fork's pull request, or one where the pull request's author has no write access. For a finding tied to no file, on a file that no policy file covers, or whose file has left the pull request, every rule on every changed file must admit the person. Never post it yourself.

**A fact beside a classifier's findings.** This applies to a \`pr/\` or \`rule/\` fact in an override that asks for less, in a rule that reads a \`repo/\` classifier with \`tools: [findings]\`:
- Put the fact below the last override that reads the classifier, or join it to a read by \`AND\` with a \`.severity\` condition.
- By \`OR\`, or below the last read where no override above is chosen, the fact alone asks for less: say so.
- Asked for "small and low risk", write, just above the fact's override, one that reads the same call, inputs included. That override repeats the rule's own verdict on every other result and on an open finding above low.

The following hold for a fact in any override. A fact that decides a \`findings\` list counts also in a rule that does not read the classifier:
- Where such a fact stands alone or by \`OR\` in an override, whoever can change it can hold back every read below it. Where no read is then reached, the classifier does not run, and its open findings clear until a read is: say so. The exception is \`run: parallel\` (\`references/tune.md\`), where below a true override it still runs and is paid for.
- Where a fact decides which \`findings\` list holds, whoever can change the fact can switch who may resolve. A finding resolved meanwhile can stay closed.
- A fact in a policy file below can switch a list above, unwarned.
- Before adding such a list or fact, read the policy files above and below.

**People:** one item, a list in brackets, or \`everyone\` or \`nobody\` alone.
- \`humans\`: every person with write access, authors included; a machine account GitHub lists as a user counts, so leave it out by login: \`"!acme-ci"\`.
- \`bots\`: every bot or App with write access, Claude's Apps and github-actions included. \`everyone\`: both.
- \`ana-acme\`: a login, in single quotes inside a condition (of the others only a \`!\` item is). \`acme/payments\`: a team of the repository's organization. \`bot:acme-fixer\`: a bot, without \`[bot]\`; \`bot:claude\` is either of Anthropic's Apps. \`pr/authors\`, \`pr/opened_by\`: whoever the fact holds.
- \`"!item"\` takes accounts away: always quoted, beside an item without \`!\`. A blank after the \`!\` is refused.

Order never matters, and whoever is both named and left out is out. Only three facts stand in a list: \`pr/authors\`, \`pr/opened_by\` and \`pr/approved_by\`, the last never in \`seats\`. Named without \`!\`, \`pr/authors\` counts only an author whom GitHub ties to the pull request, and in a \`findings\` list a bot only if it opened the pull request. A team that does not exist, or is secret, has no members, so behind \`!\` it leaves nobody out. Another organization's team, or one that cannot be read just now, counts none of its members in \`seats\` and \`findings\`, and behind \`!\` makes the list admit nobody. On a pull request that changes a policy file, at most eight teams and eight logins are looked up: a team that cannot be found or is another organization's, and a login with no write access, draw a warning, and the rest are reported as not looked up.

\`bots\`, \`everyone\`, \`bot:claude\`, and \`pr/opened_by\` on a pull request that one of Claude's Apps opened, let Claude's approval fill a seat where the verdict says \`approves\`: the check can then turn green with no person's approval. A classifier's own run may close its own findings under any list, \`nobody\` too (for Code Review, on the conditions in "After a failed Code Review: when a resolve counts"). Otherwise, in a \`findings\` list they never let Claude in for a \`repo/\` classifier. For Code Review's own threads \`bots\`, \`everyone\` and \`bot:claude\` do: the resolve of any Claude session under Claude's Apps then counts, so Claude alone can turn a failed review into a pass. Say so, and write them there only on the person's word; \`"!bot:claude"\` beside them leaves Claude out (for \`everyone\`, \`[humans, bots, "!bot:claude"]\`), and \`"!pr/authors"\` does on a pull request that one of Claude's Apps opened, where its resolve may otherwise count or not. See "After a failed Code Review: when a resolve counts".

**Paths.** \`*\` stays in one folder; \`**\` crosses folders, dot folders too, as a whole segment: \`**/*.go\`, not \`**.go\`. \`{a,b}\`, \`[ab]\`, \`?\` work. A pattern with no slash and no \`**\` matches only in the policy file's own folder. A folder is \`dir/**\`; a bare \`dir\` matches nothing in it. \`dir/**\` also matches the path \`dir\` itself, such as a symlink or a submodule. No leading or trailing slash, \`./\` or \`..\`. \`"!pattern"\` takes files out of **this rule only**, and \`"!@name"\` a local's list of patterns; a rule needs one item without \`!\`. A path starting with \`@\` or \`!\` takes a backslash in front, in single quotes.

**Conditions.** \`true\`, \`false\`, or one double-quoted string, name on the left. Operators \`=\`, \`!=\`, \`<\`, \`<=\`, \`>\`, \`>=\`. \`AND\`, \`OR\` in capitals, one kind per level, parentheses to mix; no \`NOT\`. No arithmetic and no function either, and a condition never names files: \`paths\` does that. A condition is true, false or cannot be judged. \`ANY\` or \`ALL\` stands before \`pr/authors\` and \`pr/approved_by\`, and nowhere else. \`ANY pr/authors = bots\`: one of them is in the list. \`ALL\` with \`=\`: every one is. \`ANY\` with \`!=\`: one of them is not. \`ALL\` with \`!=\`: none is. On an empty list both are false with \`=\` and true with \`!=\`. A bare \`pr/authors = bots\` is refused. Asking for more review, write \`ANY pr/authors\`; asking for less, \`ALL\`.
- \`pr/files_changed\`, \`pr/files_added\`, \`pr/files_removed\`, \`pr/diff_lines\`: a number or another count, over the whole pull request, uncovered files too (a rename's new name counts as added, its old name as removed; where the same rules match both names, \`pr/files_changed\` and \`rule/files_changed\` mostly count it once). A binary file added or edited, or a mode change, counts as over any number of lines. A Git LFS file may count only its pointer: catch such paths by path, not size. \`rule/files_changed\`, \`rule/files_added\`, \`rule/files_removed\`: among this rule's \`paths\`.
- \`pr/authors\`: \`ANY\` or \`ALL\`, \`=\` or \`!=\`, people; everyone who wrote or pushed a commit, and the opener. \`pr/approved_by\`: the same, or \`= empty\`, \`!= empty\`; never an author; refused in a seat's \`from\`. \`= empty\` takes no \`ANY\` or \`ALL\`. It holds whoever approved since the diff last changed, each a person with write access: never one whom only \`reuse\` keeps, and never a bot, so \`ANY pr/approved_by = bot:acme-fixer\` is never true, though that bot's approval can fill a seat. \`pr/opened_by\`: \`=\` or \`!=\`; one account, so no \`ANY\` or \`ALL\`; says nothing of who wrote the commits. \`pr/base\`: \`"pr/base = 'release/**'"\`; one pattern in single quotes or a list of them, matched like \`paths\`, capitals as spelt; \`=\`: it matches one, \`!=\`: none.
- **Where \`pr/authors\` or \`pr/approved_by\` cannot be judged,** the rule is held, together, to its own verdict and to every override that it could still pick. After a reopening, or a push that replaced earlier commits (mostly a force-push or a rebase), \`ALL pr/authors\` can no longer be judged true, nor \`ANY pr/authors\` false. Nor can \`pr/authors\` be judged where the answer hangs on an author with no write access, or on one whom Claude Approvals is not sure of. After such a push no condition on \`pr/approved_by\` can be judged either, once somebody other than the opener has approved. And while a person with write access who approved an earlier diff has not approved again, a condition that one more approver could change cannot be judged: \`ANY pr/approved_by = acme/leads\` can be true, never false.
- \`claude/code_review\`: \`= pass\`, \`= fail\`, \`!=\`. A file that reads it can start its reviews, billed, even where Code Review is switched off for the repository or the organization: Claude Approvals then asks for them itself (when it asks, and where it asks for none: \`references/tune.md\`, "What runs when"). A pass does not mean that Code Review read every changed file, and no condition tells how much it read: where that matters, ask more of large pull requests (\`pr/files_changed\`, \`pr/diff_lines\`). After a failed review, listed accounts' resolves alone turn \`= fail\` into \`= pass\`, with no new review ("After a failed Code Review: when a resolve counts"). Closing a finding fixes nothing, so a later review can pass with it unfixed: where that matters, keep a reviewer who is not an author. Never resolve a thread yourself unasked, and leave \`@claude approvals resolve\` to the person.
- \`claude/code_review(level=deep)\`: \`quick\`, \`standard\`, \`deep\`; how thorough the review is. Where no enforced rule that matches the pull request's files names a level, the review runs at the level in Code Review's settings, and a pass at any level counts. Where such rules name levels, in any \`if\` or under \`advisory\`, one review runs at the deepest and all of them read it. A rule whose own \`if\` is false still counts for the level, which goes by \`paths\` alone. A review that ran lighter than asked, or with no level, does not count: the check can read \`Code Review ran below the rule's level\` or \`Code Review's result has no review level\` until one at that level or deeper answers. Claude Approvals can ask for that review itself, and it is billed. A rule that observes asks for no level.
- \`claude/code_review.severity\`: \`none\`, \`minimal\`, \`low\`, \`medium\`, \`high\`, \`critical\`, six operators; the worst open finding of the run that the name or call before it reads, never of all runs. Code Review gives only \`none\`, \`minimal\`, \`high\`.
- \`claude/diff\`: \`trivial\`, \`same_intent\`, \`different\`; only under \`reuse\`. \`repo/<name>\`: see \`references/classifiers.md\`.
- \`= error\`, \`= incomplete\`: the run ended with no result (a \`repo/\` run reads \`incomplete\` where it had started work and ended by itself, \`error\` where it could not start, broke off, stored nothing or answered but could not be trusted, and neither where it can add reviewers and stored nothing, or its answer was dropped or put off: \`references/classifiers.md\`; Code Review mostly reads \`incomplete\` where it stopped short or finished with no verdict, though a review cut short can still read \`pass\` or \`fail\`). \`=\` only, never under \`reuse\`, above the overrides that read the result or in the same one: below them it is not read.

**\`reuse\`.** \`reuse: { seats: "claude/diff <= same_intent" }\`, with classifiers' names as further keys; a rule that names a classifier and leaves it out of \`reuse\` does not keep its result. \`reuse: "claude/diff <= same_intent"\` stands for \`seats\` and every classifier the rule reads. \`false\` drops the result; \`true\` draws a warning. Refused: a bare word, the keys \`claude\` and \`claude/diff\`, a condition on \`= error\` or \`= incomplete\`. A kept approval fills a set that leaves authors out only where the \`seats\` condition compares \`claude/diff\`, and not always then. Where a \`seats\` condition is set and not \`false\`, past holders of the author's seat can count too: two of them, or one beside the latest commit's author, can fill \`seats: 2\` with nobody approving, and more of them can fill a larger number.
- **Who has a say.** A rule with no \`reuse\` keeps nothing once a push changes one of its files, so a \`"**"\` rule that asks for people and writes none cancels every narrower rule's \`seats\` line. \`reuse: false\` drops every classifier's result on the rule's files, and the approval of each person whom the rule could count: whoever the items without \`!\` in its sets name, and anyone where an item is a fact or a team that could not be read. So a \`"!"\` item keeps a person out of the rule's seats, yet the rule can still drop their approval. An override's \`reuse\` replaces the rule's whole value: a name that its map leaves out keeps nothing. For a classifier's result, every policy file from the changed file's directory up to the root has a say, through its enforced rules that match that file, marked \`nested: inherit\` or not: where a root rule reads \`repo/x\` and has no line for it, a line in the directory's file alone keeps nothing.
- **What no \`reuse\` keeps.** A push that changes a protected file ends every earlier approval and every earlier result. A condition on \`claude/diff\` mostly does not keep a \`repo/\` classifier's result while it has a finding open, where an enforced rule that matches a file of the pull request reads its \`.severity\`; for more, and for Code Review, see \`references/tune.md\`, "reuse for cost". In a set whose \`from\` is anything but \`humans\` alone, a kept approval fills a seat only if one of the rule's files was also in the diff that the person approved.
- **What \`claude/diff\` compares.** For \`seats\`, today's diff with the commit that each approval was given on. For a result, with the last evaluation and, from the second push that changes the diff after its run, also with what that run read. A result kept so lasts four such pushes at most; then the classifier runs again.
- **Whatever \`reuse\` keeps, what a classifier left is cleared once no rule reaches it:** its findings are resolved, and the reviewers and labels that it added are removed. A rule does not reach a classifier that it reads only below its first true override, nor one that only its overrides read while its own \`if\` is false.

**\`locals\` and \`use\`.** A local holds text, a number, \`true\`/\`false\`, a list, or one map; \`"@name"\` can stand for an item or the whole of \`paths\`, a list of people, \`verdict\`, \`seats\` or \`override\`; or, inside a condition, a number, a list of people or of branch patterns, a whole condition or a classifier's call, which \`.severity\` or an output can follow (\`"@deep_review.severity <= low"\`); never in \`mode\`, \`nested\`, \`run\`, \`version\` or \`purpose\`. A local is seen in its file and the files below, where a file's own local of the same name wins: search them before removing one, since an unknown name refuses the file. A path pattern in a local reads as if written in the file that uses it, not where the local is written. \`"!@name"\`, as an item of \`paths\` or of a list of people, leaves out what the local holds. Where a local may stand, a backslash keeps an \`@\` plain: \`'\\@x'\`. On a rule \`use\` copies maps of \`verdict\`, \`override\`, \`if\`, \`paths\`, \`reuse\`, \`advisory\`, \`findings\`; on an override, \`verdict\` and \`findings\`.

**Limits,** past which the file is refused: 256 patterns in a rule (\`"!"\` items not counted); 16 overrides in a rule and 128 in a file; 512 rules; 512 locals; 8 names under one \`use\`; 8 sets in one \`seats\`; 16 sets under \`resolution\`; 10 teams in a list or one \`seats\`; 16 repository classifiers and 32 runs in a file; a \`purpose\` of 1,000 characters; a condition of 4,096, with 8 levels of parentheses; 1,024 entries in a list; 384 KiB. Past 1,024 policy files in the repository, or 8 MiB of them together, none is read. An override in a shared local counts once for each rule that uses it.

## Messages

On a pull request (not a fork's) that changes a policy file or classifier folder, problems are reported in the part titled "Policy files in this change". A **refusal** means the file does not load: mend it as the sentence says, but ask if that could make merging easier. A **warning** fails nothing: explain it plainly and ask whether it is meant. Where one says that the check left something out ("not checked", "could not compare", "stopped early"), a green does not cover that: say so, and pass on what the warning asks.

- **Mend, do not delete:** deleting a refused line often loosens the rule. Write what it meant (\`purpose\`, \`git log -p\`), then look again at who must approve.
- **Broken on the default branch:** restore what it last asked, nothing looser.
- **One fault hides the next:** a YAML fault is shown alone. Fix it, then check again.
- **Do not rewrite a rule only to silence a warning.** A loosening on purpose draws one: say it is expected.
- A verdict that "asks nobody to approve" when "a classifier has no result": have that verdict ask for \`seats: [{ count: 1, from: [humans, "!pr/authors"] }]\`.
- A list that "admits Claude" or "admits github-actions": name who is meant, or add \`"!bot:claude"\`, \`"!bot:github-actions"\` (for \`everyone\`, write \`[humans, bots, "!bot:claude", "!bot:github-actions"]\`).
- A person on the list who "can fill this seat themselves" (a note): a member's own pull request meets the set. Add \`"!pr/authors"\`, if somebody else should look.

"custom classifiers are not enabled for this repository", "their results do not count in this check": no file is at fault; tell the user to contact Anthropic support. Where the summary says instead that custom classifiers "do not run for this repository yet", the Claude organization has added no repository of the GitHub account that owns this one: an admin of that organization adds one in Code Review's settings, which also turns on paid Code Review for the repository added; after that a push or a rerun evaluates a pull request. Until then a policy file that names a \`repo/\` classifier is refused, under \`mode: observe\` too, on every pull request that it covers. Removing the classifier can make merging easier: only if asked. Where the default branch's copy already names it, the pull request that takes the name out gets the same refusal, so where the check is required, somebody who can bypass the branch rules must merge it. "which is our fault and not the file's": report it to Anthropic.
